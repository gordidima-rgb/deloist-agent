# Веб-версия (облако «всегда включено»)

Решения владельца, 13.11.2026:
- **Контейнер на каждого пользователя.** Внутри тот же `deloist --server` под Linux, свои данные, headless-браузер. Функции и вид совпадают с ПК, потому что код один. Второй серверной программы не пишем.
- **Обновления с GitHub.** Push в `main` сам выкатывается на тестовый адрес (аналог Deloist Dev). Тег выпуска от `release.ps1` выкатывается пользователям, как и ПК-версия.
- **Хостинг.** Российская версия — в облаке в РФ (провайдера выбрать по ценам на день выбора). Международная версия — позже, на отдельном сервере.
- Образец формы: `openbot.run/app`. В roadmap уже был пункт «Страница `/app` на deloist.ru — web-клиент к программе через тот же API».

## Что уже есть в коде (проверено 13.11.2026, `e138aba`)
- `src/main.rs:356`, режим `--server` (`run_server`): тот же `server::router`, без окна и трея, вход по одноразовой ссылке `?boot=` (`guard.rs`).
- `bind_address` (`main.rs:166`) разрешает только loopback: сервер умеет запускать команды, в сеть его отдавать нельзя. В облаке это правило остаётся. Наружу смотрит только шлюз, контейнер доступен только ему.
- `tao`/`wry`/`tray-icon` стоят в общих зависимостях. Под Linux они тянут GTK/WebKit, поэтому для сервера их нужно вынести в фичу `desktop`.
- `cfg(windows)` встречается в 15 файлах: account, browser, desktop, dock, drivers/acp, drivers/cli, main, mcp, obscura, pets, process, providers, runtime, system, tools.
- Цели Linux в тулчейне нет (только `x86_64-pc-windows-gnullvm`). CI (`.github/workflows`) нет.

## Этапы
1. **Linux-сборка.** Фича `desktop` (по умолчанию включена) для tao/wry/tray. `cargo build --no-default-features` под `x86_64-unknown-linux-gnu`; собирать в Docker или в GitHub Actions, не на этой машине. Windows-модули (dock, pets, screen, desktop) под Linux не собираются, их кнопки в интерфейсе скрываются по флагу из `/api/settings`.
2. **Облачный режим `--cloud`.** Вход не по `?boot=`, а по подписанному шлюзом токену (ключ шлюза в env контейнера). Браузер бота — Chromium внутри контейнера. CLI-агенты (Claude Code, Codex) ставятся в образ или выключены. Проверка по чек-листу защиты из CLAUDE.md.
3. **Изоляция.** Пользователь запускает в контейнере любые команды. Нужны gVisor или Kata, лимиты CPU/RAM/диска, запрет выхода во внутреннюю сеть провайдера и в метаданные облака, отдельный том данных. Это дизайн защиты: делает архитектор (Opus) с проверяющим Sonnet.
4. **Шлюз на deloist.ru `/app`.** Вход через существующий аккаунт (`server-side/`). Запуск, усыпление после N минут простоя и пробуждение контейнера, прокси HTTP и WebSocket на контейнер. Оплата тарифа «всегда включено» через тот же кошелёк и ЮKassa. Код живёт в репозитории сайта (`Documents\Deloist`), а не здесь.
5. **CI/CD.** GitHub Actions: push в `main` → образ `:main` → тестовый стенд обновляется сам. Тег `v*` → образ `:vX.Y.Z` → шлюз перезапускает контейнеры пользователей на новый образ при следующем пробуждении. Данные лежат на томе и переживают обновление.

## Этап 2 — схема архитектора (13.11.2026)
Ветки от `feat/linux-build`, каждая в своём worktree.

**2а. Вход через шлюз (`feat/cloud-auth`, защита).**
- Облачный режим включается так: `--server` + `CREW_CLOUD=1`. Без любой из обязательных переменных программа не стартует:
  - `CREW_GATEWAY_PUBKEY` — открытый ключ Ed25519 шлюза, hex;
  - `CREW_USER_ID`;
  - `CREW_PUBLIC_ORIGIN`, например `https://u-<id>.app.deloist.ru`.
- Каждому пользователю — свой поддомен: тогда cookie и Origin разных клиентов не пересекаются.
- Вход: шлюз уводит браузер на `GET /auth/gateway?t=<payload>.<sig>`.
  - payload `{uid, exp, nonce}` в base64url, подпись Ed25519 закрытым ключом шлюза.
  - Контейнер проверяет подпись открытым ключом и что `uid == CREW_USER_ID`.
  - `exp` не дальше 60 с от текущего времени; `nonce` одноразовый, хранится в памяти до истечения.
  - Затем ставит cookie `HttpOnly; Secure; SameSite=Strict; Path=/`.
  - Закрытого ключа в контейнере нет: взломанный контейнер не выпустит вход в чужой.
- В облачном режиме `?boot=` выключен: одноразовая ссылка в журнале контейнера — лишний вход.
- Host/Origin: к `127.0.0.1:<port>` и `localhost:<port>` добавляется ровно один публичный origin. WebSocket проверяется так же.
- Bind: не-loopback (`HOST=0.0.0.0`) разрешён только в облачном режиме. На ПК правило «только эта машина» не меняется.
- Ключ программы (`runtime.json`) и `human_only` не меняются.
- Тесты в `tests/safety/security.rs`:
  - чужая подпись, чужой uid, просроченный и повторный токен;
  - чужой Host и Origin;
  - `?boot=` в облаке;
  - старт без переменных;
  - не-loopback без облачного режима.
- После круга исполнителя — проверяющий Sonnet только на чтение.

- **Ревью защиты 2а, круг 1 (13.11.2026):** критичных находок нет.

    - имя cookie `__Host-` в облаке;
    - не принимать `:443` в origin и слабый ключ.
  - Круг 2 сделан: `4e89daa`, CI зелёный (run 43453930553). Все пункты ревью закрыты тестами.

- Поиск альтернатив 13.11.2026. Лицензии сверены через GitHub API, память — из чужих статей, нами не замерена:
